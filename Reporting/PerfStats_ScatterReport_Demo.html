Stutter Score: Frame Time vs Displayed Time

Mouse wheel to zoom · drag to pan

Both are 0–100 smoothness scores (higher = better; 100 = no detected stutter). Frame Time measures rendering-pipeline consistency (how evenly the app submits frames); Displayed Time measures perceived visual smoothness (how evenly frames actually land on screen). A perfect 100 on Frame Time but much lower Displayed Time indicates downstream (vsync/compositor/driver) is causing visible hitches.

Top 10 Best / Worst Performing Tables

Ranked by a composite Performance Score (0–100, higher is better). Each table's captures are averaged, then the table is percentile-ranked against every other table on the metrics below, which are blended using these weights (missing metrics are skipped and the remaining weights re-normalized):
• 60% DisplayedTime stutter score -- the capture tool's recommended perceived-smoothness metric (already blends 99.5%ile/avg frame-time delta, std dev, and animation error internally)
• 25% Average FPS -- raw throughput (StutterScoreDT self-normalizes to each table's own frame rate, so this is needed to catch slow-but-smooth tables)
• 15% FPS 1% Low / FPS Average -- tail consistency (how close the worst 1% of frames stay to the average), independent of the other two
Most of the weight is delegated to the capture tool's recommended perceived-smoothness score (DisplayedTime), which already blends the frame-pacing metrics internally — so std dev and animation error aren't scored again separately. Raw FPS is retained because that score self-normalizes to each table's own frame rate and is otherwise blind to a table running smoothly but slow. Treat this as a starting point for investigation, not an absolute verdict. A ⚠ marks a table that's also in the Recommended Re-runs list below, since a flagged capture can pull a table's ranking in either direction.
